\begin{abstract}
本实验以一段包含函数、循环、分支和输入输出的 SysY 程序观察 Clang/LLVM 的处理过程，并独立编写 LLVM IR 与 RV64 汇编，用六组输入核对运行结果。实验中检查了预处理文本、LLVM IR、汇编和 ELF 目标文件，也观察了链接后程序如何解析运行库函数。优化部分记录本例在 x86-64 与 RV64 目标上的不同变化。进阶部分从源码构建 AscendNPU-IR 的 \code{bishengir-opt}，按上游测试命令运行 PlanMemory 和 InjectSync，并用上游 FileCheck 断言验证输出。两组 Before/After 均已保存。

\noindent\textbf{关键词：} 编译器；Clang；LLVM IR；RISC-V；ABI；MLIR；lowering
\end{abstract}

\section{引言}

本次作业需要将中间产物分别保存下来，再检查每一步具体做了什么。LLVM IR 可用于追踪源程序中的变量和控制流；RISC-V 汇编则展示参数、返回值和局部变量如何使用寄存器与栈帧。

将求和程序作为示例：计数器 $i$ 从 1 增加到输入 $n$，偶数项按 $2i$ 累加，奇数项按 $i$ 累加。程序包含局部变量、算术、比较、条件分支、循环、函数调用和运行库输入输出，覆盖作业要求观察的主要结构。后续实现使用同一组输入。

先观察 Clang 生成的中间文件和目标文件，再对照 LLVM IR 的基本块结构，完成手写 IR 与汇编，最后比较优化结果并记录 AscendNPU IR 的 Pass 实验。正文只保留理解这些结果所需的代码和数据；完整输入、命令与日志放在仓库对应目录中。

\section{实验对象与工具环境}

\subsection{示例程序}

本次实验使用同一个程序。SysY 源文件 \code{source/example.sy} 如下。

\begin{lstlisting}
int calc(int n) {
    int i = 1;
    int sum = 0;
    while (i <= n) {
        if (i % 2 == 0) { sum = sum + i * 2; }
        else            { sum = sum + i;     }
        i = i + 1;
    }
    return sum;
}

int main() {
    int n;      n = getint();
    int result; result = calc(n);
    putint(result);
    return 0;
}
\end{lstlisting}

程序从 $i=1$ 开始循环，直到 $i>n$ 后返回累加值。为让 Clang 直接处理，\code{source/example_clang.c} 保留相同算法，只补充 \code{getint}/\code{putint} 的函数声明。固定输入为 $1,2,3,4,5,10$，预期结果分别为 $1,5,8,16,21,85$。这组结果由程序语义确定，再用于比较三个实现。

\subsection{LLVM IR 生成}

以下命令输出 LLVM IR：
\begin{lstlisting}
clang -S -emit-llvm -O0 source/example_clang.c -o generated/example.ll
\end{lstlisting}
命令生成 \code{generated/example.ll}。在这份 \code{-O0} IR 中，函数和控制流已显式写出；局部变量通过 \code{alloca} 取得栈槽，再由 \code{load}/\code{store} 读写。第 4 节进一步对照了这些指令与源程序的关系。

\subsection{链接}

本实验先分别生成 \code{example.o} 与 \code{host_runtime.o}，再用 Clang 驱动显式链接。日志显示驱动调用系统链接器，并加入启动文件和 C 库。链接器把 \code{example.o} 中对 \code{getint}/\code{putint} 的引用与 runtime 中的定义对应起来，再处理重定位并生成可执行文件 \code{generated/reference_linked}。它的六组输出与基准一致。单独的 \code{example.o} 仍是可重定位文件，也保留未定义的外部符号，因此不能独立运行。

从这些文件可以看到，预处理结果仍是源文本，\code{.ll} 显示控制流和运算，\code{.s} 面向具体处理器，而 \code{.o} 已将指令编码并记录尚待链接器处理的引用。各阶段产物与相应职责由此对应起来。

\subsection{手写 LLVM IR}

基于 CFG 独立编写了 \code{llvm/manual.ll}，没有复制 Clang 的 IR。手写版使用 \code{while.cond} 等语义化块名；形参 \code{n} 直接作为 SSA 值使用，只有 \code{i} 和 \code{sum} 保存在栈槽中。下面列出循环条件和回边，完整模块保存在 \code{llvm/manual.ll}。

\begin{lstlisting}
define i32 @calc(i32 %n) {
entry:
  %i.addr = alloca i32, align 4
  %sum.addr = alloca i32, align 4
  store i32 1, i32* %i.addr, align 4      ; i = 1
  store i32 0, i32* %sum.addr, align 4    ; sum = 0
  br label %while.cond

while.cond:
  %i.cond = load i32, i32* %i.addr, align 4
  %continue = icmp sle i32 %i.cond, %n    ; i <= n
  br i1 %continue, label %if.cond, label %while.end

if.cond:
  %i.parity = load i32, i32* %i.addr, align 4
  %remainder = srem i32 %i.parity, 2      ; i % 2
  %is.even = icmp eq i32 %remainder, 0
  br i1 %is.even, label %if.then, label %if.else

  ; 两个累加分支更新 sum 后进入 if.end

if.end:
  %i.current = load i32, i32* %i.addr, align 4
  %i.next = add nsw i32 %i.current, 1     ; i = i + 1
  store i32 %i.next, i32* %i.addr, align 4
  br label %while.cond                    ; while 的回边

while.end:
  %sum.result = load i32, i32* %sum.addr, align 4
  ret i32 %sum.result
}
\end{lstlisting}

\code{while.cond} 用条件分支决定继续循环还是退出；两个累加分支在 \code{if.end} 汇合，随后无条件跳回循环条件。Clang 接受完整的手写 IR，并将它与 \code{host_runtime.c} 链接。六组固定输入均通过，完整结果见 \code{outputs/manual-llvm-test.txt}。

\section{RISC-V 汇编与 ABI}

\subsection{参考汇编与调用约定}

使用 Clang 14 交叉生成 RV64 参考汇编（\code{--target=riscv64-unknown-elf -march=rv64gc -mabi=lp64d}），并将后端输出与手写实现对照。\code{calc} 的序言和奇偶判断片段如下：

\begin{lstlisting}
calc:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    addi s0, sp, 32
    sw   a0, -20(s0)
    ...
.LBB0_1:
    lw   a1, -24(s0)      # i
    lw   a0, -20(s0)      # n
    blt  a0, a1, .LBB0_6
    ...
.LBB0_2:
    lwu  a0, -24(s0)      # i % 2 的替代实现
    srli a1, a0, 31
    add  a1, a1, a0
    andi a1, a1, -2
    subw a0, a0, a1
    bne  a0, zero, .LBB0_4
\end{lstlisting}

与手写版本相比，这次 Clang 输出的 \code{calc} 与手写版都使用 32 字节栈帧，\code{ra}、\code{s0} 和局部变量的位置也相同。两版对奇偶性的处理不同：Clang 把已知除数为 2 的余数计算化成一组移位和算术指令；手写版直接用 \code{remw}。\code{rv64gc} 包含整数乘除扩展，因此 \code{remw} 是可用指令，Clang 选择算术展开并非因为架构没有取余操作。这个例子中 \code{i} 从正数 1 开始递增，所以该变换与程序使用范围相符。两版的 \code{main} 栈帧也不同：Clang -O0 使用 48 字节，手写版使用 16 字节，反映出未优化代码和人工组织值的方式不同；这不代表某一版运行更快。

\subsection{手写汇编}

手写 \code{riscv/manual.s} 独立遵守同一约定：序言建立栈帧并保存 \code{ra}/\code{s0}，循环条件用 \code{blt} 在 \code{i > n} 时退出，奇偶判断用 \code{remw} 加 \code{beqz}，偶数项用 \code{slliw} 左移一位代替乘 2，累加用 \code{addw}，循环尾递增 \code{i} 后无条件跳回条件块。控制流标签与第 4 节的 LLVM 基本块一一对应。

\begin{lstlisting}
calc:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    addi s0, sp, 32
    sw   a0, -20(s0)       # 保存参数 n
    ...
.Lwhile_cond:
    lw   t0, -24(s0)       # i
    lw   t1, -20(s0)       # n
    blt  t1, t0, .Lwhile_end
.Lif_cond:
    li   t1, 2
    remw t2, t0, t1
    beqz t2, .Lif_then
    ...
.Lwhile_end:
    lw   a0, -28(s0)       # 返回值
    ld   s0, 16(sp)
    ld   ra, 24(sp)
    addi sp, sp, 32
    ret
\end{lstlisting}

完整实现见 \code{riscv/manual.s}。其中 \code{main} 用 16 字节栈帧保存 \code{ra}，依次调用 \code{getint}、\code{calc}、\code{putint}；整数参数和返回值都经 \code{a0} 传递。

\section{优化观察：-O0 与 -O2}

以同一份 C 文件生成两种优化级别的 LLVM IR、x86-64 汇编和 RV64 汇编，再比较实际 diff。下面的观察只针对这个程序和这两种目标。

\subsection{从内存槽到 SSA}

在这份 \code{-O0} IR 中，局部变量通过栈槽和 \code{load}/\code{store} 访问；\code{-O2} 结果则把这些变量保存在 SSA 值中，并用 \code{phi} 传递循环迭代间的值。统计结果为 \code{alloca/load/store} 从 6/11/9 降到 0/0/0，\code{phi} 从 0 增至 32。主要变化是同一状态不再通过内存读写表达。

\subsection{奇偶判断被改写成位运算}

源程序用 \texttt{i \% 2 == 0} 选择分支。\code{-O2} 把奇偶判断从取模与分支改写为位运算。RV64 的 \code{calc} 中，奇偶位决定左移 0 位还是 1 位，因而两条累加路径可以合成一条：

\begin{lstlisting}
calc:
    li   a1, 0
    blez a0, .LBB0_3
    li   a2, 1
.LBB0_2:
    mv   a3, a2
    not  a2, a2
    andi a2, a2, 1
    sllw a2, a3, a2        # i << (i 为偶数 ? 1 : 0)
    addw a1, a1, a2        # sum += 该项
    addiw a2, a3, 1
    blt  a3, a0, .LBB0_2
.LBB0_3:
    mv   a0, a1
    ret
\end{lstlisting}

\code{not}/\code{andi} 生成移位量，\code{sllw} 再按该值左移：偶数项乘 2，奇数项保持原值。这样，输出汇编不再保留原来的 \code{if/else}。优化后的 \code{calc} 也不再需要栈帧，因为它不调用其他函数且只使用临时寄存器。

\subsection{两种目标的低层差异}

同一份较高层的优化结果，最终仍要由目标后端决定怎样使用本机指令。

x86-64 的结果中可以看到四个 \code{i32} 组成的向量运算、XMM 寄存器和 \code{paddd}；循环末尾还保留处理不足四个元素的路径。RV64 目标为 \code{rv64gc}，不含 RVV 扩展，所以输出仍是标量循环，没有 RVV 向量指令。两种目标都把 \code{calc} 内联进 \code{main}，但向量化结果不同。

两种目标生成的汇编长度变化方向不同：x86-64 因向量循环和内联而增加，RV64 因控制流与栈访问减少而变短。汇编文本行数不能替代运行时间、代码体积或能耗测量；本实验没有测量这些指标，因此不据此推断性能提升。

这条概念路线中，高层表示主要描述“两个向量逐元素相加”；到了 HIVM，内存空间和搬运步骤已显式出现。官方 VecAdd 样例使用 16 个 \code{i16} 元素：A、B、C 位于 GM，输入通过 \code{hivm.hir.load} 搬入 UB，在 UB 上执行 \code{hivm.hir.vadd}，再由 \code{hivm.hir.store} 写回 GM。下列代码是对上游文件的结构摘录，省略了完整类型和入口属性，并非从 Arith/Tensor 实际 lowering 得到的输出。\cite{ascend-framework,ascend-vecadd}

\begin{lstlisting}
func.func @add(%a: memref<16xi16, #hivm.address_space<gm>>,
               %b: memref<16xi16, #hivm.address_space<gm>>,
               %c: memref<16xi16, #hivm.address_space<gm>>) {
  %ua = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.load ins(%a : ...) outs(%ua : ...) // GM -> UB
  %ub = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.load ins(%b : ...) outs(%ub : ...) // GM -> UB
  %uc = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.vadd ins(%ua, %ub : ...) outs(%uc : ...)
  hivm.hir.store ins(%uc : ...) outs(%c : ...) // UB -> GM
  return
}
\end{lstlisting}

代码摘录保留了本例的关键操作。\code{memref.alloc} 标出 UB 临时区，\code{load}/\code{store} 标出 GM 与 UB 之间的数据移动；算术本身由 \code{vadd} 表达。硬件相关信息进入 IR 后，后续 Pass 才能针对这些存储和执行约束继续处理。

PlanMemory 根据临时 buffer 的生命周期和目标硬件约束安排片上地址；在这个用例中，它把 \code{memref.alloc} 改写为带偏移的 \code{hivm.hir.pointer_cast}。实验采用上游 \code{plan-memory.mlir} 中的 \code{test\_mem\_allocate\_basic}：其中四个 UB buffer 都是 $16\times16\times16$ 的 \code{f16} 张量，每个占 8192 字节。测试自带的默认策略命令为：

\subsection{实测二：InjectSync 表达流水线依赖}

第二个上游用例 \code{test\_mem\_injct\_sync\_basic} 只有 \code{load}、\code{vadd} 和 \code{store} 三个操作，输入中没有同步指令。运行测试中的 \code{-hivm-inject-sync -hivm-lower-multi-buffer-counter} 后，IR 增加了以下依赖关系：

\begin{lstlisting}
hivm.hir.load ins(%arg0 : ...<gm>) outs(%0 : ...<ub>)
hivm.hir.set_flag[<PIPE_MTE2>, <PIPE_V>, <EVENT_ID0>]
hivm.hir.wait_flag[<PIPE_MTE2>, <PIPE_V>, <EVENT_ID0>]
hivm.hir.vadd ins(%0, %2 : ...) outs(%0 : ...)
hivm.hir.set_flag[<PIPE_V>, <PIPE_MTE3>, <EVENT_ID0>]
hivm.hir.wait_flag[<PIPE_V>, <PIPE_MTE3>, <EVENT_ID0>]
hivm.hir.store ins(%0 : ...<ub>) outs(%arg1 : ...<gm>)
hivm.hir.pipe_barrier[<PIPE_ALL>]
\end{lstlisting}

MTE2 与 MTE3 表示数据搬运流水，V 表示向量计算流水。Pass 在 load 后加入 MTE2 到 V 的 flag/wait，在 store 前加入 V 到 MTE3 的 flag/wait，并在函数末尾加入一条 \code{PIPE\_ALL} barrier。统计结果是 2 条 \code{set\_flag}、2 条 \code{wait\_flag} 和 1 条 \code{pipe\_barrier}；Before 文件中的真实指令数为 0。这组结果说明，IR 中的操作顺序并不等同于不同硬件流水线之间的完成依赖；Pass 将需要等待的依赖显式写出。Before/After 文件保存在 \code{mlir/outputs/}。\cite{ascend-sync-test,ascend-passes}

\section{结论}

作为编译原理初学者，本次实验将源程序、LLVM IR、汇编、目标文件和可执行程序联系起来。检查 \code{example.o} 可见，它仍是 \code{ET\_REL} 文件，并保留对 \code{getint}/\code{putint} 的引用；显式链接之后，这些引用才由 runtime 提供定义。由此可以区分汇编器与链接器的职责。

LLVM IR 中，循环条件、奇偶分支和回边由基本块与 \code{br} 指令表示，并据此完成了手写 IR。RV64 汇编展示了同一控制流在目标架构上的实现：参数和返回值使用 \code{a0}，\code{calc} 通过栈帧保存局部变量。手写版本与 Clang 输出的栈帧布局接近，但奇偶判断采用了不同指令。

优化实验显示，\code{-O2} 会改变变量表示，并化简分支和算术；最终是否向量化还取决于目标架构。本例在 x86-64 上出现向量运算，在不含 RVV 的 RV64 目标上仍是标量循环。由于没有测量运行时间，本实验只比较代码结构，不据此判断运行速度。

AscendNPU IR 实验展示了硬件约束如何进入较低层表示。PlanMemory 用例将四个临时分配转换为偏移为 0 的 \code{pointer\_cast}，计算操作保持不变；InjectSync 则在数据搬运与向量计算之间加入 flag/wait，并在函数末尾加入 barrier。三条上游 RUN 命令及其 FileCheck 断言均通过。Arith/Tensor 到 HFusion 的部分仍是资料整理，实测范围从 HIVM 开始；本次没有编译 kernel 或在 NPU 上运行。

整体上，本次实验完成了处理流程观察、手写实现和固定用例验证，并通过真实 Pass 输出补充了 Ascend IR 实验。编译器仍有许多实现细节未涉及；当前保存的产物能够说明各阶段表示发生的变化，也限定了结论适用的范围。
