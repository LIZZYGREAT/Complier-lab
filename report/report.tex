\begin{abstract}
本实验以一段包含函数、循环、分支和输入输出的 SysY 程序观察 Clang/LLVM 的处理过程，并独立编写 LLVM IR 与 RV64 汇编，用六组输入核对运行结果。实验中检查了预处理文本、LLVM IR、汇编和 ELF 目标文件，也观察了链接后程序如何解析运行库函数。优化部分记录本例在 x86-64 与 RV64 目标上的不同变化。进阶部分从源码构建 AscendNPU-IR 的 \code{bishengir-opt}，按上游测试命令运行 PlanMemory 和 InjectSync，并用上游 FileCheck 断言验证输出。两组 Before/After 均收录于报告附录。

\noindent\textbf{关键词：} 编译器；Clang；LLVM IR；RISC-V；ABI；MLIR；lowering
\end{abstract}

\section{引言}
\label{sec:intro}

本次作业需要将中间产物分别保存下来，再检查每一步具体做了什么。LLVM IR 可用于追踪源程序中的变量和控制流；RISC-V 汇编则展示参数、返回值和局部变量如何使用寄存器与栈帧。

将求和程序作为示例：计数器 $i$ 从 1 增加到输入 $n$，偶数项按 $2i$ 累加，奇数项按 $i$ 累加。程序包含局部变量、算术、比较、条件分支、循环、函数调用和运行库输入输出，覆盖作业要求观察的主要结构。后续实现使用同一组输入。

先观察 Clang 生成的中间文件和目标文件，再对照 LLVM IR 的基本块结构，完成手写 IR 与汇编，最后比较优化结果并记录 AscendNPU IR 的 Pass 实验。正文保留理解这些结果所需的代码和数据；完整输入、实现以及必要命令与过程证据收录于附录，读者仅凭本报告即可查阅。附录材料索引见附录~\ref{app:index}。

\subsection{示例程序与语言特性}
\label{sec:sample}

本次实验使用同一个程序。SysY 源程序如下，完整输入版本见附录~\ref{app:source}。

\begin{lstlisting}
int calc(int n) {
    int i = 1;
    int sum = 0;
    while (i <= n) {
        if (i % 2 == 0) { sum = sum + i * 2; }
        else            { sum = sum + i;     }
        i = i + 1;
    }
    return sum;
}

int main() {
    int n;      n = getint();
    int result; result = calc(n);
    putint(result);
    return 0;
}
\end{lstlisting}

程序从 $i=1$ 开始循环，直到 $i>n$ 后返回累加值。为让 Clang 直接处理，附录~\ref{app:source} 中的 C 输入版本保留相同算法，只补充 \code{getint}/\code{putint} 的函数声明。

\subsection{LLVM IR 的生成命令与产物}
\label{sec:irgen}

以下命令输出 LLVM IR：
\begin{lstlisting}
clang -S -emit-llvm -O0 source/example_clang.c -o generated/example.ll
\end{lstlisting}
命令生成 \code{generated/example.ll}。在这份 \code{-O0} IR 中，函数和控制流已显式写出；局部变量通过 \code{alloca} 取得栈槽，再由 \code{load}/\code{store} 读写。第~\ref{sec:cfg}~节进一步对照了这些指令与源程序的关系。

\subsection{汇编：机器码、符号与重定位}

\subsection{链接：运行库解析与可执行文件}
\label{sec:link}

本实验先分别生成 \code{example.o} 与 \code{host_runtime.o}，再用 Clang 驱动显式链接。日志显示驱动调用系统链接器，并加入启动文件和 C 库。链接器把 \code{example.o} 中对 \code{getint}/\code{putint} 的引用与 runtime 中的定义对应起来，再处理重定位并生成可执行文件 \code{generated/reference_linked}。它的六组输出与基准一致。单独的 \code{example.o} 仍是可重定位文件，也保留未定义的外部符号，因此不能独立运行。

从这些文件可以看到，预处理结果仍是源文本，\code{.ll} 显示控制流和运算，\code{.s} 面向具体处理器，而 \code{.o} 已将指令编码并记录尚待链接器处理的引用。各阶段产物与相应职责由此对应起来。

各阶段完整命令、目标文件检查与链接日志摘录见附录~\ref{app:pipeline} 和附录~\ref{app:elf}；自动生成的基础 IR 与 RV64 参考汇编见附录~\ref{app:generated}。

\subsection{手写 LLVM IR 与生成结果对比}
\label{sec:manualir}

基于 CFG 独立编写了附录~\ref{app:manualir} 中的 LLVM 模块，没有复制 Clang 的 IR。手写版使用 \code{while.cond} 等语义化块名；形参 \code{n} 直接作为 SSA 值使用，只有 \code{i} 和 \code{sum} 保存在栈槽中。下面列出循环条件和回边，完整模块见附录~\ref{app:manualir}。

\begin{lstlisting}
define i32 @calc(i32 %n) {
entry:
  %i.addr = alloca i32, align 4
  %sum.addr = alloca i32, align 4
  store i32 1, i32* %i.addr, align 4      ; i = 1
  store i32 0, i32* %sum.addr, align 4    ; sum = 0
  br label %while.cond

while.cond:
  %i.cond = load i32, i32* %i.addr, align 4
  %continue = icmp sle i32 %i.cond, %n    ; i <= n
  br i1 %continue, label %if.cond, label %while.end

if.cond:
  %i.parity = load i32, i32* %i.addr, align 4
  %remainder = srem i32 %i.parity, 2      ; i % 2
  %is.even = icmp eq i32 %remainder, 0
  br i1 %is.even, label %if.then, label %if.else

  ; 两个累加分支更新 sum 后进入 if.end

if.end:
  %i.current = load i32, i32* %i.addr, align 4
  %i.next = add nsw i32 %i.current, 1     ; i = i + 1
  store i32 %i.next, i32* %i.addr, align 4
  br label %while.cond                    ; while 的回边

while.end:
  %sum.result = load i32, i32* %sum.addr, align 4
  ret i32 %sum.result
}
\end{lstlisting}

\code{while.cond} 用条件分支决定继续循环还是退出；两个累加分支在 \code{if.end} 汇合，随后无条件跳回循环条件。Clang 接受完整的手写 IR，并将它与附录~\ref{app:runtime} 的宿主机运行库链接。六组固定输入均通过，逐组原始结果见附录~\ref{app:tests}。

\subsection{RISC-V 参考汇编与调用约定}
\label{sec:abi}

使用 Clang 14 交叉生成 RV64 参考汇编（\code{--target=riscv64-unknown-elf -march=rv64gc -mabi=lp64d}），并将后端输出与手写实现对照。\code{calc} 的序言和奇偶判断片段如下：

\begin{lstlisting}
calc:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    addi s0, sp, 32
    sw   a0, -20(s0)
    ...
.LBB0_1:
    lw   a1, -24(s0)      # i
    lw   a0, -20(s0)      # n
    blt  a0, a1, .LBB0_6
    ...
.LBB0_2:
    lwu  a0, -24(s0)      # i % 2 的替代实现
    srli a1, a0, 31
    add  a1, a1, a0
    andi a1, a1, -2
    subw a0, a0, a1
    bne  a0, zero, .LBB0_4
\end{lstlisting}

与手写版本相比，这次 Clang 输出的 \code{calc} 与手写版都使用 32 字节栈帧，\code{ra}、\code{s0} 和局部变量的位置也相同。两版对奇偶性的处理不同：Clang 把已知除数为 2 的余数计算化成一组移位和算术指令；手写版直接用 \code{remw}。\code{rv64gc} 包含整数乘除扩展，因此 \code{remw} 是可用指令，Clang 选择算术展开并非因为架构没有取余操作。这个例子中 \code{i} 从正数 1 开始递增，所以该变换与程序使用范围相符。两版的 \code{main} 栈帧也不同：Clang -O0 使用 48 字节，手写版使用 16 字节，反映出未优化代码和人工组织值的方式不同。

\subsection{手写 RISC-V 汇编}
\label{sec:manualasm}

附录~\ref{app:manualasm} 中的手写汇编独立遵守同一约定：序言建立栈帧并保存 \code{ra}/\code{s0}，循环条件用 \code{blt} 在 \code{i > n} 时退出，奇偶判断用 \code{remw} 加 \code{beqz}，偶数项用 \code{slliw} 左移一位代替乘 2，累加用 \code{addw}，循环尾递增 \code{i} 后无条件跳回条件块。控制流标签与第~\ref{sec:cfg}~节的 LLVM 基本块一一对应。

\begin{lstlisting}
calc:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    addi s0, sp, 32
    sw   a0, -20(s0)       # 保存参数 n
    ...
.Lwhile_cond:
    lw   t0, -24(s0)       # i
    lw   t1, -20(s0)       # n
    blt  t1, t0, .Lwhile_end
.Lif_cond:
    li   t1, 2
    remw t2, t0, t1
    beqz t2, .Lif_then
    ...
.Lwhile_end:
    lw   a0, -28(s0)       # 返回值
    ld   s0, 16(sp)
    ld   ra, 24(sp)
    addi sp, sp, 32
    ret
\end{lstlisting}

\section{优化探索：-O0 与 -O2}
\label{sec:optimization}

\subsection{对照方法与总体变化}
\label{sec:optmethod}

以同一份 C 文件生成两种优化级别的 LLVM IR、x86-64 汇编和 RV64 汇编，再比较实际 diff。下面的观察只针对这个程序和这两种目标。

\begin{table}[H]
  \centering\small
  \caption{LLVM IR 指令数量与结构变化}
  \begin{tabularx}{\textwidth}{P{3.2cm}P{3.6cm}Y}
    \toprule
    指标 & -O0 & -O2 \\
    \midrule
    \code{alloca} & 6 & 0 \\
    \code{load} & 11 & 0 \\
    \code{store} & 9 & 0 \\
    \code{phi} & 0 & 32 \\
    局部变量表示 & 栈槽 + 内存读写 & SSA 临时值 + 循环 \code{phi} \\
    奇偶判断 & \code{srem} + \code{icmp eq} + \code{br} & \code{and}/\code{xor}/\code{shl} 位运算 \\
    \code{main} 对 \code{calc} 的调用 & 存在 \code{call @calc} & 已内联；\code{@calc} 定义因外部可见而保留 \\
    \bottomrule
  \end{tabularx}
\end{table}

\subsection{从内存槽到 SSA}

在这份 \code{-O0} IR 中，局部变量通过栈槽和 \code{load}/\code{store} 访问；\code{-O2} 结果则把这些变量保存在 SSA 值中，并用 \code{phi} 传递循环迭代间的值。统计结果为 \code{alloca/load/store} 从 6/11/9 降到 0/0/0，\code{phi} 从 0 增至 32。主要变化是同一状态不再通过内存读写表达。

\subsection{奇偶判断与分支化简}

源程序用 \texttt{i \% 2 == 0} 选择分支。\code{-O2} 把奇偶判断从取模与分支改写为位运算。RV64 的 \code{calc} 中，奇偶位决定左移 0 位还是 1 位，因而两条累加路径可以合成一条：

\begin{lstlisting}
calc:
    li   a1, 0
    blez a0, .LBB0_3
    li   a2, 1
.LBB0_2:
    mv   a3, a2
    not  a2, a2
    andi a2, a2, 1
    sllw a2, a3, a2        # i << (i 为偶数 ? 1 : 0)
    addw a1, a1, a2        # sum += 该项
    addiw a2, a3, 1
    blt  a3, a0, .LBB0_2
.LBB0_3:
    mv   a0, a1
    ret
\end{lstlisting}

\code{not}/\code{andi} 生成移位量，\code{sllw} 再按该值左移：偶数项乘 2，奇数项保持原值。这样，输出汇编不再保留原来的 \code{if/else}。优化后的 \code{calc} 也不再需要栈帧，因为它不调用其他函数且只使用临时寄存器。

\subsection{x86-64 与 RV64 的目标差异}

同一份较高层的优化结果，最终仍要由目标后端决定怎样使用本机指令。

x86-64 的结果中可以看到四个 \code{i32} 组成的向量运算、XMM 寄存器和 \code{paddd}；循环末尾还保留处理不足四个元素的路径。RV64 目标为 \code{rv64gc}，不含 RVV 扩展，所以输出仍是标量循环，没有 RVV 向量指令。两种目标都把 \code{calc} 内联进 \code{main}，但向量化结果不同。

\subsection{优化观察的结论边界}
\label{sec:optlimit}

两种目标生成的汇编长度变化方向不同：x86-64 因向量循环和内联而增加，RV64 因控制流与栈访问减少而变短。汇编文本行数不能替代运行时间、代码体积或能耗测量；本实验没有测量这些指标，因此不据此推断性能提升。

生成命令、统计口径及带上下文的原始对照片段见附录~\ref{app:optimization}。上述计数针对完整宿主机 IR 模块，不能与仅统计 \code{calc} 的结果混用。

\subsection{多级 IR 与渐进式 lowering}
\label{sec:multilevel}

前文的 LLVM IR 已显式表示变量读写和分支；面向 NPU 时，还需要表达张量形状、存储位置、数据搬运和硬件流水线。MLIR 允许编译器用不同 Dialect 保留这些层次的信息，再逐步 lowering。较高层的张量与算子语义有利于融合和 tiling；HIVM 则能表达 GM、UB 以及对应的数据搬运和向量运算。图~\ref{fig:lowering} 是依据课程要求与官方资料整理的概念路线。\cite{mlir-lang,mlir-rationale,ascend-framework}

这条概念路线中，高层表示主要描述“两个向量逐元素相加”；到了 HIVM，内存空间和搬运步骤已显式出现。官方 VecAdd 样例使用 16 个 \code{i16} 元素：A、B、C 位于 GM，输入通过 \code{hivm.hir.load} 搬入 UB，在 UB 上执行 \code{hivm.hir.vadd}，再由 \code{hivm.hir.store} 写回 GM。下列代码是对上游文件的结构摘录。\cite{ascend-framework,ascend-vecadd}

\begin{lstlisting}
func.func @add(%a: memref<16xi16, #hivm.address_space<gm>>,
               %b: memref<16xi16, #hivm.address_space<gm>>,
               %c: memref<16xi16, #hivm.address_space<gm>>) {
  %ua = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.load ins(%a : ...) outs(%ua : ...) // GM -> UB
  %ub = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.load ins(%b : ...) outs(%ub : ...) // GM -> UB
  %uc = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.vadd ins(%ua, %ub : ...) outs(%uc : ...)
  hivm.hir.store ins(%uc : ...) outs(%c : ...) // UB -> GM
  return
}
\end{lstlisting}

代码摘录保留了本例的关键操作。\code{memref.alloc} 标出 UB 临时区，\code{load}/\code{store} 标出 GM 与 UB 之间的数据移动；算术本身由 \code{vadd} 表达。硬件相关信息进入 IR 后，后续 Pass 才能针对这些存储和执行约束继续处理。

\subsection{InjectSync：流水线依赖实测}
\label{sec:sync}

第二个上游用例 \code{test_mem_injcet_sync_basic} 只有 \code{load}、\code{vadd} 和 \code{store} 三个操作，输入中没有同步指令。运行测试中的 \code{-hivm-inject-sync -hivm-lower-multi-buffer-counter} 后，IR 增加了以下依赖关系：

\begin{lstlisting}
hivm.hir.load ins(%arg0 : ...<gm>) outs(%0 : ...<ub>)
hivm.hir.set_flag[<PIPE_MTE2>, <PIPE_V>, <EVENT_ID0>]
hivm.hir.wait_flag[<PIPE_MTE2>, <PIPE_V>, <EVENT_ID0>]
hivm.hir.vadd ins(%0, %2 : ...) outs(%0 : ...)
hivm.hir.set_flag[<PIPE_V>, <PIPE_MTE3>, <EVENT_ID0>]
hivm.hir.wait_flag[<PIPE_V>, <PIPE_MTE3>, <EVENT_ID0>]
hivm.hir.store ins(%0 : ...<ub>) outs(%arg1 : ...<gm>)
hivm.hir.pipe_barrier[<PIPE_ALL>]
\end{lstlisting}

MTE2 与 MTE3 表示数据搬运流水，V 表示向量计算流水。Pass 在 load 后加入 MTE2 到 V 的 flag/wait，在 store 前加入 V 到 MTE3 的 flag/wait，并在函数末尾加入一条 \code{PIPE_ALL} barrier。统计结果是 2 条 \code{set_flag}、2 条 \code{wait_flag} 和 1 条 \code{pipe_barrier}；Before 文件中的真实指令数为 0。这组结果说明，IR 中的操作顺序并不等同于不同硬件流水线之间的完成依赖；Pass 将需要等待的依赖显式写出。完整 Before/After 见附录~\ref{app:sync}。\cite{ascend-sync-test,ascend-passes}

\subsection{探索结果与实测边界}
\label{sec:ascboundary}

官方 VecAdd、PlanMemory 和 InjectSync 使用不同输入。两个 Pass 的单用例 Before/After 用于解释局部变换；三个上游 RUN 的 FileCheck 结果用于验证完整上游测试文件。不能将它们视为同一个 VecAdd 从高层到机器码的完整流水线转储。Arith/Tensor 与 HFusion 的路线属于资料整理，本次实测从 HIVM 开始，未安装 CANN、配置驱动、生成并运行 kernel 目标文件或上板。完整材料见附录~\ref{app:ascend}。

\section{结论}
\label{sec:conclusion}

本次实验将源程序、LLVM IR、汇编、目标文件和可执行程序联系起来。检查 \code{example.o} 可见，它仍是 \code{ET_REL} 文件，并保留对 \code{getint}/\code{putint} 的引用；显式链接之后，这些引用才由 runtime 提供定义。由此可以区分汇编器与链接器的职责。

LLVM IR 中，循环条件、奇偶分支和回边由基本块与 \code{br} 指令表示，并据此完成了手写 IR。RV64 汇编展示了同一控制流在目标架构上的实现：参数和返回值使用 \code{a0}，\code{calc} 通过栈帧保存局部变量。手写版本与 Clang 输出的栈帧布局接近，但奇偶判断采用了不同指令。

优化实验显示，\code{-O2} 会改变变量表示，并化简分支和算术；最终是否向量化还取决于目标架构。本例在 x86-64 上出现向量运算，在不含 RVV 的 RV64 目标上仍是标量循环。

AscendNPU IR 实验展示了硬件约束如何进入较低层表示。PlanMemory 用例将四个临时分配转换为偏移为 0 的 \code{pointer_cast}，计算操作保持不变；InjectSync 则在数据搬运与向量计算之间加入 flag/wait，并在函数末尾加入 barrier。三条上游 RUN 命令及其 FileCheck 断言均通过。Arith/Tensor 到 HFusion 的部分仍是资料整理，实测范围从 HIVM 开始。

整体上，本次实验完成了处理流程观察、手写实现和固定用例验证，并通过真实 Pass 输出补充 Ascend IR 实验。

\begin{lstlisting}[caption={完整手写 LLVM 模块}]
; Hand-written LLVM IR for source/example.sy.
; The control-flow graph is expressed with named basic blocks and memory slots.

source_filename = "manual.ll"
target triple = "x86_64-pc-linux-gnu"

declare i32 @getint()
declare void @putint(i32)

define i32 @calc(i32 %n) {
entry:
  %i.addr = alloca i32, align 4
  %sum.addr = alloca i32, align 4
  store i32 1, i32* %i.addr, align 4
  store i32 0, i32* %sum.addr, align 4
  br label %while.cond

while.cond:
  %i.cond = load i32, i32* %i.addr, align 4
  %continue = icmp sle i32 %i.cond, %n
  br i1 %continue, label %if.cond, label %while.end

if.cond:
  %i.parity = load i32, i32* %i.addr, align 4
  %remainder = srem i32 %i.parity, 2
  %is.even = icmp eq i32 %remainder, 0
  br i1 %is.even, label %if.then, label %if.else

if.then:
  %sum.even = load i32, i32* %sum.addr, align 4
  %i.even = load i32, i32* %i.addr, align 4
  %twice.i = mul nsw i32 %i.even, 2
  %sum.even.next = add nsw i32 %sum.even, %twice.i
  store i32 %sum.even.next, i32* %sum.addr, align 4
  br label %if.end

if.else:
  %sum.odd = load i32, i32* %sum.addr, align 4
  %i.odd = load i32, i32* %i.addr, align 4
  %sum.odd.next = add nsw i32 %sum.odd, %i.odd
  store i32 %sum.odd.next, i32* %sum.addr, align 4
  br label %if.end

if.end:
  %i.current = load i32, i32* %i.addr, align 4
  %i.next = add nsw i32 %i.current, 1
  store i32 %i.next, i32* %i.addr, align 4
  br label %while.cond

while.end:
  %sum.result = load i32, i32* %sum.addr, align 4
  ret i32 %sum.result
}

define i32 @main() {
entry:
  %n = call i32 @getint()
  %result = call i32 @calc(i32 %n)
  call void @putint(i32 %result)
  ret i32 0
}

\subsection{完整手写 RISC-V 汇编}
\label{app:manualasm}

\begin{lstlisting}[caption={完整手写 RV64 汇编}]
    .section .text
    .align 2

    .globl calc
    .type calc, @function
calc:
    addi sp, sp, -32
    sd ra, 24(sp)
    sd s0, 16(sp)
    addi s0, sp, 32
    sw a0, -20(s0)       # n
    li t0, 1
    sw t0, -24(s0)       # i = 1
    sw zero, -28(s0)     # sum = 0

.Lwhile_cond:
    lw t0, -24(s0)       # i
    lw t1, -20(s0)       # n
    blt t1, t0, .Lwhile_end

.Lif_cond:
    li t1, 2
    remw t2, t0, t1
    beqz t2, .Lif_then
    j .Lif_else

.Lif_then:
    lw t0, -28(s0)       # sum
    lw t1, -24(s0)       # i
    slliw t1, t1, 1      # 2 * i
    addw t0, t0, t1
    sw t0, -28(s0)
    j .Lif_end

.Lif_else:
    lw t0, -28(s0)       # sum
    lw t1, -24(s0)       # i
    addw t0, t0, t1
    sw t0, -28(s0)

.Lif_end:
    lw t0, -24(s0)
    addiw t0, t0, 1
    sw t0, -24(s0)
    j .Lwhile_cond

.Lwhile_end:
    lw a0, -28(s0)       # integer return value
    ld s0, 16(sp)
    ld ra, 24(sp)
    addi sp, sp, 32
    ret
    .size calc, .-calc

    .align 2
    .globl main
    .type main, @function
main:
    addi sp, sp, -16
    sd ra, 8(sp)
    call getint          # input/return value in a0
    call calc            # argument and return value in a0
    call putint          # output argument in a0
    li a0, 0
    ld ra, 8(sp)
    addi sp, sp, 16
    ret
    .size main, .-main

    .section .note.GNU-stack,"",@progbits
\end{lstlisting}

	sllw	a2, a3, a2
	addw	a1, a1, a2
	addiw	a2, a3, 1
	blt	a3, a0, .LBB0_2
.LBB0_3:
	mv	a0, a1
	ret
.Lfunc_end0:
	.size	calc, .Lfunc_end0-calc

	.globl	main
	.p2align	1
	.type	main,@function
main:
	addi	sp, sp, -16
	sd	ra, 8(sp)
	call	getint
	li	a1, 0
	blez	a0, .LBB1_3
	li	a2, 1
\end{lstlisting}

RV64 的 O0 完整参考汇编见附录~\ref{app:generated}。O2 片段可见标量寄存器与位运算；该目标为 \code{rv64gc}，没有启用 RVV。x86-64 片段中的 XMM 与 \code{paddd} 对应向量运算。以上仅报告结构变化，不报告耗时、能耗或速度提升。

\subsection{构建版本、配置、故障处理与完整链接补丁}
\label{app:ascbuild}

原实验使用 CMake 4.4.4、Ninja 1.13.2；AscendNPU-IR 提交为 \code{2ac1b376}，LLVM 子项目提交为 \code{06913395}，产出的工具为 bishengir-opt 2.0.0 / LLVM 19.1.7 Release。原实验采用六路编译，并记录约 4.8 GiB 内存峰值，未触发 3 GiB swap。

以下配置取自成功构建所用脚本。\code{REPO_DIR} 为固定版本上游源码的本地位置，\code{LLVM_SRC} 为其 \code{third-party/llvm-project} 子模块，\code{BUILD_DIR} 为构建目录，须按本地实际位置设置；采用用户级虚拟环境中的 CMake/Ninja。

    -DLLVM_PARALLEL_LINK_JOBS=1 \
    -DBUILD_SHARED_LIBS=OFF \
    -DBSPUB_DAVINCI_BISHENGIR=ON \

构建经历四轮尝试：先遇到生成头文件 \code{SkewShapeTable.inc} 的依赖缺口，再遇到关闭 HIVMC 导致的未定义符号，最后遇到 HIVMCLib 与 A3/A5 的静态库循环。先单独构建 \code{BiShengIRSkewShapeTable} 生成头文件，并将 \code{BISHENGIR_BUILD_HIVMC} 恢复为上游默认的 ON，最终以以下链接组补丁解决循环。复现时应在配置与编译前，将下列补丁应用于固定版本源码；前面的配置清单已经采用成功配置。尝试添加 PUBLIC 依赖与 \code{LINK_INTERFACE_MULTIPLICITY} 时，CMake 因循环包含 \code{OBJECT_LIBRARY} 拒绝配置，该尝试已回退。补丁只调整该可执行文件的链接参数，不修改 Pass；它是本地处理方式，不是上游正式修复。以下为完整补丁。

\begin{lstlisting}[caption={完整静态库链接组补丁}]
diff --git a/bishengir/tools/bishengir-opt/CMakeLists.txt b/bishengir/tools/bishengir-opt/CMakeLists.txt
index 8b61528..b188f13 100644
--- a/bishengir/tools/bishengir-opt/CMakeLists.txt
+++ b/bishengir/tools/bishengir-opt/CMakeLists.txt
@@ -43,4 +43,14 @@ endif()
 
 target_link_libraries(bishengir-opt PRIVATE ${LIBS})
 
+# BiShengIRHIVMCLib 与 BiShengIRHIVMCLibA3/A5 之间存在静态库循环：
+# A3/A5 引用 HIVMCLib 的 setSanitizerAddrArgName，而 HIVMCLib 又调用
+# runHIVMCCompileA3/A5。静态库单遍扫描会漏解该循环，导致
+# "undefined reference to setSanitizerAddrArgName"。
+# 这里用 LINK_GROUP:RESCAN 让链接器对这组库重复扫描
+# （在 GNU 工具链上生成 --start-group/--end-group），
+# 不引入 CMake 层面的依赖环，因此不会与 OBJECT_LIBRARY 冲突。
+target_link_libraries(bishengir-opt PRIVATE
+  "$<LINK_GROUP:RESCAN,BiShengIRHIVMCLib,BiShengIRHIVMCLibA3,BiShengIRHIVMCLibA5>")
+
 mlir_check_all_link_libraries(bishengir-opt)
\end{lstlisting}
