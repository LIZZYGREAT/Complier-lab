\begin{abstract}
本文以一个含函数、while、if/else、取模和整数输入输出的 SysY 风格程序为贯穿案例，使用 Clang 14 观察预处理、词法/语法/语义分析与 IR 生成、x86-64 汇编、ELF 目标文件和显式链接的完整过程，并通过实际 \code{readelf} 输出核对节区、符号与重定位项。随后根据源程序语义独立手写 LLVM IR 与 RV64 汇编，对照控制流图与栈帧布局逐条说明设计意图，并分别链接运行库验证。六组输入在宿主机 reference、手写 LLVM 和 QEMU/RISC-V 上均得到 1、5、8、16、21、85。优化对比显示，Clang -O2 消除了该模块中的 alloca/load/store，并在 x86-64 上生成四 lane 向量运算；RV64 目标保留标量循环并内联 calc。最后依据 LLVM 与 AscendNPU-IR 官方材料分析 VecAdd 的多层 MLIR lowering，并解读官方 PlanMemory 测试用例；该部分为资料与源码分析，没有运行本机 Ascend 编译器或设备。全部实验由脚本驱动，可逐阶段复现。

\noindent\textbf{关键词：} 编译器；Clang；LLVM IR；RISC-V；ABI；MLIR；lowering
\end{abstract}

\section{引言}

编译器把源程序逐步转换为可执行程序。理解每一步的输入、输出和符号关系，有助于分清预处理、编译、汇编和链接的职责。LLVM IR 适合观察语言结构如何变为控制流和算术指令；RISC-V 汇编则展示调用约定、寄存器和栈帧如何落实到目标架构。

本实验固定一个程序，避免不同算法导致比较基准变化。程序令 $i$ 从 1 递增到输入 $n$，若 $i$ 为偶数则将 $2i$ 加入 sum，否则将 $i$ 加入 sum，最后输出 sum。程序覆盖局部整型变量、赋值、加法、乘法、取模、比较、条件分支、循环、函数参数、函数返回和运行库调用。所有实现都使用同一输入集合验证。

全文围绕四个问题组织。第一，预处理、编译、汇编、链接各自做了什么，产物之间是什么关系（第 3 节）；第二，源程序的条件与循环如何变成 LLVM 基本块和 \code{br}，又如何能独立手写出一份等价 IR（第 4 节）；第三，同一逻辑在 RV64 上如何落到寄存器、栈帧和调用约定（第 5 节）；第四，优化级别和抽象层次的变化会带来什么（第 7、8 节）。所有结论都来自本机真实产物，原始命令、输出和中间文件分别保存在 \code{scripts/}、\code{logs/} 和 \code{records/} 中，第 9 节给出复现入口。

\section{实验对象与工具环境}

\subsection{贯穿程序}

整次作业只使用一个程序，避免更换算法导致比较基准漂移。其 SysY 源程序 \code{source/example.sy} 如下。

\begin{lstlisting}
int calc(int n) {
    int i = 1;
    int sum = 0;
    while (i <= n) {
        if (i % 2 == 0) { sum = sum + i * 2; }
        else            { sum = sum + i;     }
        i = i + 1;
    }
    return sum;
}

int main() {
    int n;      n = getint();
    int result; result = calc(n);
    putint(result);
    return 0;
}
\end{lstlisting}

该程序覆盖局部整型变量、赋值、整型常量、加法、乘法、取模、比较、\code{if/else}、\code{while}、函数定义与调用、参数传递、返回值以及运行库输入输出，足以观察编译器的主要结构。语义为：$i$ 从 1 递增到 $n$，$i$ 为偶数时累加 $2i$，否则累加 $i$，最后输出 sum。为使 Clang 能直接处理，\code{source/example_clang.c} 与 \code{example.sy} 算法完全一致，仅补充运行库声明 \code{int getint(void);} 与 \code{void putint(int x);}；宿主机验证所需的 \code{getint}/\code{putint} 由 \code{source/host_runtime.c} 以 \code{scanf}/\code{printf} 实现。固定测试集为 $n=1,2,3,4,5,10$，期望输出依次为 $1,5,8,16,21,85$；该期望值独立于任何实现，作为唯一的 Ground Truth。

\subsection{预处理}

命令 \code{clang -E source/example_clang.c -o generated/example.i} 生成预处理文件。预处理器只处理以 \code{#} 开头的指令：展开宏、插入 \code{#include} 内容、求值条件编译、处理行标记。它按行替换文本，不做词法之外的语义判断，因此不理会 \code{while}、\code{if} 的含义。本例没有宏、条件编译和头文件，\code{generated/example.i} 只有 11 行 \code{#} 行标记，其后语句与输入完全相同。

\begin{lstlisting}
# 1 "source/example_clang.c"
# 1 "<built-in>" 1
# 1 "<built-in>" 3
# 361 "<built-in>" 3
...
# 1 "source/example_clang.c" 2
int getint(void);
void putint(int x);

int calc(int n) {
    int i = 1;
    ...
\end{lstlisting}

行标记形如 \code{# 行号 "文件名" 标志}，供后续阶段和调试器把生成代码映射回源文件；\code{<built-in>} 是编译器内建的定义集合。除这 11 行标记外，\code{.i} 内容与输入逐字相同——这恰好从反面说明预处理阶段“没有做什么”：它不建立符号表、不检查类型、也不理解控制流，这些都属于下一节的编译阶段。

\subsection{LLVM IR 生成}

命令如下：
\begin{lstlisting}
clang -S -emit-llvm -O0 source/example_clang.c -o generated/example.ll
\end{lstlisting}
生成 \code{generated/example.ll}。它是与目标无关的中间表示，函数、类型、指令都在此层显式可见。\code{-O0} 下一个 \code{alloca} 对应一个局部变量，每次读写都显式 \code{load}/\code{store}，见第 4 节。

\subsection{汇编与目标文件}

\code{clang -S -O0} 生成宿主机汇编 \code{generated/example_x86.s}；\code{clang -c -O0} 继续调用集成汇编器，将汇编编码为机器码，产出 ELF64 可重定位目标文件 \code{generated/example.o}。汇编器负责指令编码、地址分配和符号表构造，此时地址尚未最终确定，因此外部引用以重定位项的形式保留。对 \code{example.o} 的实际检查结果如下。

\subsection{链接}

本实验分别生成 \code{example.o} 与 \code{host_runtime.o}，再用 Clang 驱动显式链接。日志显示 Clang 调用 \code{/usr/bin/ld}，并加入 CRT 启动对象和 \code{-lc}。链接器按符号名把各目标文件的定义与引用配对：\code{host_runtime.o} 定义 \code{getint}/\code{putint}，解决 \code{example.o} 的两个未定义符号；系统 C 库解析 runtime 中的 \code{scanf}/\code{printf}。随后合并同名节区、按最终地址应用重定位、丢弃不再需要的符号信息，生成可执行 ELF \code{generated/reference_linked}，其六组输出与 Ground Truth 一致。反过来说，单独的 \code{example.o} 既缺少两个外部函数定义，也没有进程启动代码，因此不能独立完成整个程序功能；\code{getint}/\code{putint} 正是在链接阶段被解析的。

\subsection{手写 LLVM IR}

手写 \code{llvm/manual.ll} 不复用 Clang 的输出，而是按上面的 CFG 直接组织命名基本块。与自动生成版本的差异恰好说明了“人工设计”与“工具默认策略”的区别：块名是语义化的 \code{while.cond} 而不是 \texttt{\%5}；没有 \code{attributes}、\code{!llvm.loop} 等约定性元数据；\code{main} 中直接用 SSA 值传递 \code{getint} 与 \code{calc} 的返回值，不再绕经栈槽。控制流与算术指令则与源程序逐项对应。

\begin{lstlisting}
declare i32 @getint()
declare void @putint(i32)

define i32 @calc(i32 %n) {
entry:
  %i.addr = alloca i32, align 4
  %sum.addr = alloca i32, align 4
  store i32 1, i32* %i.addr, align 4      ; i = 1
  store i32 0, i32* %sum.addr, align 4    ; sum = 0
  br label %while.cond

while.cond:
  %i.cond = load i32, i32* %i.addr, align 4
  %continue = icmp sle i32 %i.cond, %n    ; i <= n
  br i1 %continue, label %if.cond, label %while.end

if.cond:
  %i.parity = load i32, i32* %i.addr, align 4
  %remainder = srem i32 %i.parity, 2      ; i % 2
  %is.even = icmp eq i32 %remainder, 0
  br i1 %is.even, label %if.then, label %if.else

if.then:
  %sum.even = load i32, i32* %sum.addr, align 4
  %i.even = load i32, i32* %i.addr, align 4
  %twice.i = mul nsw i32 %i.even, 2       ; 2 * i
  %sum.even.next = add nsw i32 %sum.even, %twice.i
  store i32 %sum.even.next, i32* %sum.addr, align 4
  br label %if.end

if.else:
  %sum.odd = load i32, i32* %sum.addr, align 4
  %i.odd = load i32, i32* %i.addr, align 4
  %sum.odd.next = add nsw i32 %sum.odd, %i.odd
  store i32 %sum.odd.next, i32* %sum.addr, align 4
  br label %if.end

if.end:
  %i.current = load i32, i32* %i.addr, align 4
  %i.next = add nsw i32 %i.current, 1     ; i = i + 1
  store i32 %i.next, i32* %i.addr, align 4
  br label %while.cond                    ; while 的回边

while.end:
  %sum.result = load i32, i32* %sum.addr, align 4
  ret i32 %sum.result
}

define i32 @main() {
entry:
  %n = call i32 @getint()
  %result = call i32 @calc(i32 %n)
  call void @putint(i32 %result)
  ret i32 0
}
\end{lstlisting}

\code{while} 没有也不需要有专门的 LLVM 指令：\code{while.cond} 计算条件、\code{br i1} 二选一，\code{if.end} 的无条件 \code{br} 跳回 \code{while.cond} 即构成回边。\code{if/else} 同样只是 \code{if.cond} 处的一次条件 \code{br} 加两个分支块，两条分支在 \code{if.end} 汇合。Clang 接受该 IR，将其与 \code{host_runtime.c} 链接为 \code{generated/manual_llvm}，六组输入全部通过（\code{outputs/manual-llvm-test.txt}）。

\subsection{参考汇编与调用约定}

RISC-V 参考汇编由 Clang 14 交叉生成（\code{--target=riscv64-unknown-elf -march=rv64gc -mabi=lp64d}），先用于观察成熟后端如何表达同一逻辑，再作为手写实现的对照。其 \code{calc} 序言为：

\begin{lstlisting}
calc:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    addi s0, sp, 32
    sw   a0, -20(s0)
    ...
.LBB0_1:
    lw   a1, -24(s0)      # i
    lw   a0, -20(s0)      # n
    blt  a0, a1, .LBB0_6
    ...
.LBB0_2:
    lwu  a0, -24(s0)      # i % 2 的替代实现
    srli a1, a0, 31
    add  a1, a1, a0
    andi a1, a1, -2
    subw a0, a0, a1
    bne  a0, zero, .LBB0_4
\end{lstlisting}

把这段与下一节的手写版本对照，可以得到三个具体结论。第一，\emph{栈帧完全一致}：Clang 同样用 32 字节帧、\code{ra} 存 \code{24(sp)}、\code{s0} 存 \code{16(sp)}、三个局部量放在 \code{-20/-24/-28(s0)}，说明手写实现在没有照抄的情况下收敛到了与真实后端相同的布局。第二，\emph{取模的实现不同}：RV64 没有硬件取余指令，\code{remw} 需要微码或库调用，因此 Clang 把 $i \bmod 2$ 展开成 \code{lwu/srli/add/andi/subw} 五条定点运算；手写版本直接用 \code{remw} 加 \code{beqz}，更贴近源程序语义但指令条数更少，这也说明“指令少”不等于“更快”。第三，\emph{\code{main} 的帧大小不同}：Clang 的 \code{main} 用 48 字节，因为它把返回值先 \code{sd} 溢出到栈再取出；手写 \code{main} 只用 16 字节，返回值始终留在 \code{a0} 中直接传递。

\subsection{手写汇编}

手写 \code{riscv/manual.s} 独立遵守同一约定：序言建立栈帧并保存 \code{ra}/\code{s0}，循环条件用 \code{blt} 在 \code{i > n} 时退出，奇偶判断用 \code{remw} 加 \code{beqz}，偶数项用 \code{slliw} 左移一位代替乘 2，累加用 \code{addw}，循环尾递增 \code{i} 后无条件跳回条件块。控制流标签与第 4 节的 LLVM 基本块一一对应。

\begin{lstlisting}
calc:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    addi s0, sp, 32
    sw   a0, -20(s0)        # n = 入参
    li   t0, 1
    sw   t0, -24(s0)        # i = 1
    sw   zero, -28(s0)      # sum = 0
.Lwhile_cond:
    lw   t0, -24(s0)        # i
    lw   t1, -20(s0)        # n
    blt  t1, t0, .Lwhile_end    # if (n < i) 退出循环
.Lif_cond:
    li   t1, 2
    remw t2, t0, t1         # i % 2
    beqz t2, .Lif_then
    j    .Lif_else
.Lif_then:
    lw   t0, -28(s0)        # sum
    lw   t1, -24(s0)        # i
    slliw t1, t1, 1         # 2 * i
    addw t0, t0, t1
    sw   t0, -28(s0)
    j    .Lif_end
.Lif_else:
    lw   t0, -28(s0)
    lw   t1, -24(s0)
    addw t0, t0, t1
    sw   t0, -28(s0)
.Lif_end:
    lw   t0, -24(s0)
    addiw t0, t0, 1         # i + 1
    sw   t0, -24(s0)
    j    .Lwhile_cond       # while 的回边
.Lwhile_end:
    lw   a0, -28(s0)        # 返回值放入 a0
    ld   s0, 16(sp)
    ld   ra, 24(sp)
    addi sp, sp, 32
    ret
\end{lstlisting}

\code{main} 只保留 16 字节栈帧用于存放 \code{ra}，连续调用 \code{getint}、\code{calc}、\code{putint}，三者之间的整数传递全部通过 \code{a0} 完成；这体现了“参数与返回值共用 \code{a0}“这一约定。

\subsection{从内存槽到 SSA}

\code{-O0} 把每个局部变量放进取址栈槽，任何读写都要经过 \code{load}/\code{store}。\code{-O2} 在 IR 上执行 mem2reg 一类变换后，可变变量成为 SSA 值；循环中跨迭代传递的量则用 \code{phi} 节点表达。本例最直观的证据是 \code{alloca/load/store} 全部归零、\code{phi} 从 0 增至 32。这解释了为什么“优化”首先改变的不是指令条数，而是\emph{值的表示方式}：寄存器化之后，后续的算术化简和向量化才有作用对象。

\subsection{奇偶判断被改写成位运算}

源程序用 \texttt{i \% 2 == 0} 选择分支。\code{-O2} 识别出这是奇偶测试，不再依赖取模。x86-64 的 IR 中可以看到 \code{and}/\code{xor}/\code{shl} 的组合，RV64 的 \code{calc} 则压缩为：

\begin{lstlisting}
calc:
    li   a1, 0
    blez a0, .LBB0_3
    li   a2, 1
.LBB0_2:
    mv   a3, a2
    not  a2, a2
    andi a2, a2, 1
    sllw a2, a3, a2        # i << (i 为偶数 ? 1 : 0)
    addw a1, a1, a2        # sum += 该项
    addiw a2, a3, 1
    blt  a3, a0, .LBB0_2
.LBB0_3:
    mv   a0, a1
    ret
\end{lstlisting}

这段代码值得逐行读。\code{not}/\code{andi} 取出 $i$ 的奇偶位再取反，得到“$i$ 为偶数时为 1，否则为 0”的移位量；\code{sllw a2, a3, a2} 做变长左移，一次性完成原程序的两个分支——偶数时左移 1 位即乘 2，奇数时左移 0 位即原值。整个 \code{if/else} 因此消失，只剩一个循环。此外 \code{calc} 在 \code{-O2} 下没有建立任何栈帧（无 \code{sp} 调整、无 \code{ra} 保存），因为优化后它已不含函数调用，成为叶子函数。

\subsection{两种目标的低层差异}

尽管 IR 是目标无关的，同一份 \code{-O2} IR 在两种后端上继续下降的结果并不相同。

x86-64 带 SSE2，且本程序的循环次数可判定，因此 loop vectorizer 把它改写为四 lane 运算：\code{O2.ll} 中出现 \code{<4 x i32>} 类型的 \code{phi} 与 \code{shl}，以及 \code{call i32 @llvm.vector.reduce.add.v4i32}，汇编中可见 XMM 寄存器和 \code{paddd}。由于 \code{calc} 不是 4 的整数倍长度也能正确退出，向量化版本还额外生成了边界与尾部路径。

RV64 目标为 \code{rv64gc}，不含 RVV 向量扩展，因此 \code{O2\_riscv.s} 仍是标量循环，没有向量寄存器指令；优化所做的只是内联与算术化简。两种目标的共同点是 \code{main} 都不再调用 \code{calc}，即函数内联在两条路径上都发生了。

\section{MLIR / AscendNPU VecAdd}

MLIR 以 operation/value/block/region 和 dialect 描述不同抽象层。多层表示的作用是让每一阶段保留它需要的信息：张量形状和算子边界便于做 fusion、tiling 与调度；进一步 lowering 后，内存位置、数据搬运和目标硬件操作才逐步明确。若过早把算子摊平成低层指令，后续优化就难直接利用张量和算子语义。LLVM IR 可作为后续通用低层表示，但它不替代前面针对张量和 NPU 硬件的抽象。\cite{mlir-lang,mlir-rationale,mlir-llvm,ascend-framework}

官方 HIVM VecAdd 文件 \code{mlir/sources/vecadd_hivm.mlir} 中，16 个 \code{i16} 元素的 A、B、C 参数位于 GM；两次 \code{hivm.hir.load} 把输入搬到 UB，\code{hivm.hir.vadd} 在 UB 上计算，\code{hivm.hir.store} 再写回 GM。这里的数据不是只标注为“向量值”，还带有存储位置和搬运路径。

\begin{lstlisting}
func.func @add(%arg0: memref<16xi16, #hivm.address_space<gm>>,
               %arg1: memref<16xi16, #hivm.address_space<gm>>,
               %arg2: memref<16xi16, #hivm.address_space<gm>>)
    attributes {hacc.entry, hacc.function_kind = #hacc.function_kind<DEVICE>} {
  %alloc   = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.load ins(%arg0 : ...<gm>) outs(%alloc   : ...<ub>)   // GM -> UB
  %alloc_0 = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.load ins(%arg1 : ...<gm>) outs(%alloc_0 : ...<ub>)   // GM -> UB
  %alloc_1 = memref.alloc() : memref<16xi16, #hivm.address_space<ub>>
  hivm.hir.vadd ins(%alloc, %alloc_0 : ...<ub>, ...<ub>) outs(%alloc_1 : ...<ub>)
  hivm.hir.store ins(%alloc_1 : ...<ub>) outs(%arg2 : ...<gm>)  // UB -> GM
  return
}
\end{lstlisting}

与高层表示相比，这里的 \code{memref.alloc} 都显式标注 \code{<ub>} 地址空间，\code{hivm.hir.load}/\code{store} 把“从哪搬到哪”写成显式指令。这正是 NPU 编程与普通标量程序的关键差别：计算必须在片上存储（UB）进行，数据必须先从全局内存（GM）搬入、算完再搬回，因此原本隐含的硬件执行策略被编码进了 IR。\cite{ascend-framework,ascend-vecadd}

\subsection{PlanMemory 上游用例分析}

PlanMemory 根据 buffer 生命周期和硬件约束规划片上地址。它把局部 \code{memref.alloc} 改写为带偏移的 \code{hivm.hir.pointer_cast}。

Ascend 上游测试文件 \code{plan-memory.mlir} 中的 \texttt{test\allowbreak\_mem\allowbreak\_allocate\allowbreak\_basic} 用例包含四个大小为 $16\times16\times16\times2=8192$ 字节的 UB 临时 buffer。其上游 RUN 命令与关键断言为：

\begin{lstlisting}
// RUN: bishengir-opt %s -hivm-plan-memory -split-input-file -verify-diagnostics | FileCheck %s
// CHECK-NOT: memref.alloc()
// CHECK: hivm.hir.pointer_cast ... offset = 0
\end{lstlisting}
\code{CHECK-NOT} 断言输出不再包含 \code{memref.alloc()}，\code{CHECK} 要求这些 buffer 被改写为带偏移的 \code{pointer_cast}。这说明 Pass 的作用不是改变计算语义，而是把“我需要一块 UB”这一抽象请求落实为“这块 UB 在各硬件缓冲区中的具体地址”。\cite{ascend-planmemory,ascend-passes,ascend-planmemory-test}

\subsection{观察范围与证据边界}

第 8 节与前七节的性质不同，必须明确区分“本机真实运行得到”和“依据官方材料分析得到”两类内容。

本机环境检查的实际结果是：系统中没有 CMake，Ninja 版本为 1.10.1，低于 AscendNPU-IR 官方构建要求的 1.12。按任务书中“环境不满足即退化为资料与源码分析”的约定，本实验没有克隆或构建 \code{bishengir-opt}，也没有运行任何 HIVM Pass。因此：

\begin{itemize}
  \item 本节的\emph{真实文件}是 \code{mlir/sources/vecadd\_hivm.mlir}（官方 16$\times$\code{i16} VecAdd）与 \code{mlir/sources/selected\_tests/plan\_memory\_input.mlir}（官方 \code{plan-memory.mlir} 的相关片段），二者来自上游仓库。
  \item 其中的 \code{RUN}/\code{CHECK} 是\emph{上游测试的期望}，不是本机产生的输出；\code{mlir/outputs/} 目录下没有 Before/After 文件，因为 Pass 未被执行。
  \item 层次图（Arith/Tensor $\to$ HFusion $\to$ HIVM $\to$ HACC/LLVM）是根据官方架构资料整理的概念主线；可以逐行核对的实物只到 HIVM 层。
  \item 没有安装完整 CANN，没有配置 Ascend 驱动，没有生成或运行 kernel \code{.o}，没有在真实 NPU 上执行。
\end{itemize}

之所以仍然保留这一节，是因为它要回答的问题——“为什么需要多层 IR”“硬件细节何时进入 IR”——在读完 HIVM 层的真实 IR 与 PlanMemory 的官方断言后已经可以回答清楚。但本报告不把这段分析表述为一次完整的编译实验结果，也不声称获得了任何 NPU 运行数据。\cite{ascend-build,ascend-readme}

\section{结论}

本文用一个包含函数、循环、分支、取模和运行库调用的 SysY 程序，走通了从源程序到可执行文件的全部环节，并在此基础上独立完成了两套手写实现。按引言提出的四个问题，可以得到以下结论。

\textbf{关于四个阶段的分工。} 预处理只做文本替换，产物仍是源文本；前端把它变成 LLVM IR，其间经过词法、语法和语义分析；汇编器把汇编变成可重定位目标文件，此时地址未定、外部符号未解；链接器才把定义与引用配对并定下最终地址。本实验的 \code{example.o} 是 \code{ET\_REL}、入口地址为 0、含两个未定义符号，而链接后的文件六组测试全部通过，这一对比即为四者职责的直接证据。

\textbf{关于 LLVM IR 到源代码的映射。} \code{-O0} 下 IR 与源程序接近一一对应：\code{alloca/load/store} 表示变量，\code{icmp}/\code{br} 表示比较与转移，\code{define/call/ret} 表示函数关系。\code{while} 和 \code{if} 都没有专用指令，它们由基本块、条件计算和 \code{br} 组合而成；循环由 \code{if.end} 跳回 \code{while.cond} 的回边体现。正因为这一映射是结构性的，才能在阅读自动生成结果之后独立重写出一份语义等价、命名更清晰的 \code{manual.ll}。

\textbf{关于 RISC-V 的落地方式。} 参数与返回值共用 \code{a0}，\code{calc} 用 32 字节栈帧保存 \code{ra}、\code{s0} 和三个局部量，控制流落为比较加条件跳转的标签结构。值得记录的是，手写版与 Clang 自动版收敛到了\emph{相同的栈帧布局}，但在取模和 \code{main} 的栈帧大小上做了不同取舍——说明 ABI 约束是刚性的，而具体实现仍留有空间。

\textbf{关于优化与抽象层次。} \code{-O2} 先改变值的表示（栈槽变 SSA，出现 32 个 \code{phi}），再重写算术（奇偶判断退化为变长左移，整个 \code{if/else} 消失），最后才由后端按目标能力决定是否向量化：x86-64 生成四 lane 运算和 \code{paddd}，RV64 因缺少 RVV 仍是标量循环。两种目标的汇编行数一增一减（87$\to$385 与 91$\to$56），说明行数不能作为优化效果的度量。MLIR 部分则从另一个方向回答了分层问题：HIVM 层把 GM/UB 地址空间和 \code{hivm.hir.load}/\code{vadd}/\code{store} 显式写入 IR，把原本隐含的硬件搬运策略变成可分析、可规划的信息，这正是“多层 IR”相对单一低层 IR 的价值所在。

\textbf{本实验的边界。} 所有前七节结论均基于本机真实产物，可用第 9 节的脚本逐阶段复现。第 8 节的 MLIR/Ascend 部分受限于环境（无 CMake、Ninja 1.10.1 低于要求的 1.12），为官方文档与上游测试用例的结构分析，没有运行 \code{bishengir-opt}，没有生成或运行 kernel，也没有在 Ascend NPU 上执行；报告中不对此作任何实测声明。
