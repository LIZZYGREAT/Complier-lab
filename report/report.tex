\begin{abstract}
本文以一个含函数、while、if/else、取模和整数输入输出的 SysY 风格程序为贯穿案例，使用 Clang 14 观察预处理、LLVM IR 生成、x86-64 汇编、ELF 目标文件和显式链接过程。随后根据源程序语义独立手写 LLVM IR 与 RV64 汇编，并分别链接运行库验证。六组输入在宿主机 reference、手写 LLVM 和 QEMU/RISC-V 上均得到 1、5、8、16、21、85。优化对比显示，Clang -O2 消除了该模块中的 alloca/load/store，并在 x86-64 上生成四 lane 向量运算；RV64 目标保留标量循环并内联 calc。最后依据 LLVM 与 AscendNPU-IR 官方材料分析 VecAdd 的多层 MLIR lowering，并解读官方 PlanMemory 测试用例；该部分为资料与源码分析，没有运行本机 Ascend 编译器或设备。

\noindent\textbf{关键词：} 编译器；Clang；LLVM IR；RISC-V；ABI；MLIR；lowering
\end{abstract}

\section{引言}

编译器把源程序逐步转换为可执行程序。理解每一步的输入、输出和符号关系，有助于分清预处理、编译、汇编和链接的职责。LLVM IR 适合观察语言结构如何变为控制流和算术指令；RISC-V 汇编则展示调用约定、寄存器和栈帧如何落实到目标架构。

本实验固定一个程序，避免不同算法导致比较基准变化。程序令 $i$ 从 1 递增到输入 $n$，若 $i$ 为偶数则将 $2i$ 加入 sum，否则将 $i$ 加入 sum，最后输出 sum。程序覆盖局部整型变量、赋值、加法、乘法、取模、比较、条件分支、循环、函数参数、函数返回和运行库调用。所有实现都使用同一输入集合验证。

\section{实验对象与工具环境}

程序语义可写为：

\begin{lstlisting}
sum = 0
for i = 1..n:
    if i % 2 == 0: sum += 2 * i
    else:          sum += i
return sum
\end{lstlisting}

工作环境为 Ubuntu 22.04.5 on WSL2，Clang 14.0.0、GCC 11.4、QEMU 7.0.0、RISC-V unknown-elf GCC 15.1、Flex 2.6.4、Bison 3.8.2。课程目录已有编译器和 SysY runtime，本实验复用其 \code{libsysy_riscv.a}；没有重新安装或改动该目录。Clang 的 RISC-V 参考目标和手写目标统一使用 \code{rv64gc/lp64d}。

\subsection{预处理}

命令 \code{clang -E source/example_clang.c -o generated/example.i} 生成预处理文件。本例没有宏、条件编译或头文件，因此 \code{.i} 主要保留原 C 语句和源文件行标记。预处理器解释预处理指令并输出供后续前端处理的源文本；本例中的 if、while 语义由后续编译阶段处理。

\subsection{编译与 LLVM IR}

命令如下：
\begin{lstlisting}
clang -S -emit-llvm -O0 source/example_clang.c -o generated/example.ll
\end{lstlisting}
命令对 \code{source/example_clang.c} 编译并生成 \code{generated/example.ll}。Clang 前端完成词法、语法和语义处理，再生成 IR；LLVM 中端可在 IR 上优化，后端按目标架构选择指令。本次 -O0 IR 中，局部变量由 alloca/load/store 表示，比较使用 icmp，while 和 if/else 通过 br 与基本块表达，函数调用和返回体现为 call/ret。

\subsection{汇编与目标文件}

\code{clang -S -O0} 生成宿主机 x86-64 汇编 \code{generated/example_x86.s}。Clang \code{-c} 将 C 文件继续编译、汇编成 ELF64 可重定位目标文件 \code{generated/example.o}；该文件的 ELF 类型为 REL，包含 \code{.text}、符号表和重定位项。符号表显示 calc、main 已定义，getint 和 putint 仍为未定义符号。它们的调用位置需要由链接器结合运行库解析。

\subsection{链接}

本实验分别生成 \code{example.o} 与 \code{host_runtime.o}，再用 Clang 驱动显式链接。日志显示 Clang 调用 \code{/usr/bin/ld}，并加入 CRT 启动对象和 \code{-lc}。\code{host_runtime.o} 定义 getint/putint，系统 C 库解析 scanf/printf。链接器应用重定位、合并输入节区并生成最终可执行 ELF。单独的 example.o 既没有完整的外部符号定义，也不是可直接执行的进程映像。

Clang -O0 生成的 calc 使用数字标签。入口块初始化 i 和 sum 后进入 \texttt{\%5}；\texttt{\%5} 用 \code{icmp sle} 计算 $i \le n$。真分支进入 \texttt{\%9} 判断 $i\bmod 2$，两个分支 \texttt{\%13}、\texttt{\%18} 分别计算偶数项和奇数项，并汇入 \texttt{\%22}。\texttt{\%22} 执行 $i{+}{+}$ 后无条件跳回 \texttt{\%5}，构成 while 回边；假分支到 \texttt{\%25} 读取 sum 并返回。

\section{RISC-V 汇编与 ABI}

RISC-V 参考汇编由 Clang 14 交叉生成。手写 \code{riscv/manual.s} 将 n、i、sum 保存于 calc 栈帧；while 条件用 \code{blt n,i,while_end} 判断退出；\code{remw} 与 \code{beqz} 选择奇偶分支；偶数项用 \code{slliw} 乘 2，累加用 \code{addw}，循环尾递增 i 并跳回条件块。

\section{优化观察：-O0 与 -O2}

\begin{table}[H]
  \centering\small
  \caption{LLVM IR 中间表示指令数量}
  \begin{tabularx}{0.75\textwidth}{Yrr}
    \toprule
    LLVM IR 指令数量 & -O0 & -O2 \\
    \midrule
    alloca & 6 & 0 \\
    load & 11 & 0 \\
    store & 9 & 0 \\
    \bottomrule
  \end{tabularx}
\end{table}

\code{-O2} 将可变局部量改写为 SSA 值和循环 phi，消除了显式栈槽读写，并把余数/if 奇偶计算改成位运算与移位。x86-64 IR 出现四 lane \code{<4 x i32>} 运算和 vector reduce；汇编中可见 XMM 与 \code{paddd}。calc 仍有外部可见定义，但 main 内的调用已被内联。x86 汇编行数从 87 变为 385，增加来自向量化循环体和内联代码，行数本身不表示速度或代码尺寸。

RV64 目标为 rv64gc，不包含 RVV 扩展。其 -O2 汇编仍为标量循环，没有向量寄存器指令；优化将 calc 内联进 main，并化简奇偶累加。RV64 汇编行数从 91 变为 56。本实验没有测量执行时间，因此不据此推断性能提升。

\section{MLIR / AscendNPU VecAdd}

MLIR 以 operation/value/block/region 和 dialect 描述不同抽象层。多层表示的作用是让每一阶段保留它需要的信息：张量形状和算子边界便于做 fusion、tiling 与调度；进一步 lowering 后，内存位置、数据搬运和目标硬件操作才逐步明确。若过早把算子摊平成低层指令，后续优化就难直接利用张量和算子语义。LLVM IR 可作为后续通用低层表示，但它不替代前面针对张量和 NPU 硬件的抽象。\cite{mlir-lang,mlir-rationale,mlir-llvm,ascend-framework}

\subsection{PlanMemory 上游用例分析}

PlanMemory 根据 buffer 生命周期和硬件约束规划片上地址。它把局部 \code{memref.alloc} 改写为带偏移的 \code{hivm.hir.pointer_cast}。

Ascend 上游测试文件 \code{plan-memory.mlir} 中的 \texttt{test\allowbreak\_mem\allowbreak\_allocate\allowbreak\_basic} 用例包含四个大小为 $16\times16\times16\times2=8192$ 字节的 UB 临时 buffer。其上游 RUN 命令为：

\begin{lstlisting}
bishengir-opt %s -hivm-plan-memory -split-input-file -verify-diagnostics | FileCheck %s
\end{lstlisting}
文件中的 \code{CHECK} 断言输出不再包含 \code{memref.alloc()}，并要求这四处 buffer 对应偏移 0 的 \code{pointer_cast}。这说明 Pass 会把抽象分配请求改写为显式地址表达。\cite{ascend-planmemory,ascend-passes,ascend-planmemory-test}

本机没有 CMake，Ninja 1.10.1 低于 AscendNPU-IR 官方构建要求的 1.12；因此没有构建 \code{bishengir-opt}。此处的 \code{CHECK} 是上游测试期望，未在本机执行，也没有保存为真实 Before/After 输出。没有安装完整 CANN，没有生成或运行 kernel \code{.o}，也没有在 Ascend NPU 上执行。\cite{ascend-build,ascend-readme}

\section{结论}

通过同一 SysY 程序，实验观察了 Clang 从预处理文本、LLVM IR、宿主机汇编到 ELF 目标文件和链接结果的流程。手写 LLVM IR 和 RV64 汇编均遵循源程序控制流与函数语义，并通过六组输入验证。优化对照显示，优化会改变值表示、循环形态和目标指令选择，且不同后端得到不同的向量化结果。MLIR 的多层 dialect 保留张量/算子信息，并在 lowering 中逐步引入内存与硬件细节；PlanMemory 上游测试说明了 HIVM 地址规划的预期结构变化。本机没有运行该 Pass 或 NPU 程序。
